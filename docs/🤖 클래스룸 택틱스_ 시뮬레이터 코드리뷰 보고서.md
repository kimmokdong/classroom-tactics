## 2. 🤖 봇(AgentBot) 행동 로직 심층 검증

봇들이 시너지를 배제하고 오직 깡스탯과 밸류만으로 덱을 구성하는지 각 레벨별 행동 로직을 검증하였습니다.

### 🥉 6레벨 / 7레벨 덱 로직 (`simulate6L_7L`)
설명서의 목표(6렙 2코 3성 4개, 7렙 3코 3성 3개)를 채우기 위한 리롤 및 구매 로직이 작성되어 있습니다. 그러나 **잠금(Lock) 판단 조건**에서 심각한 로직 불일치가 발견되었습니다.

> **설명서 요구사항**: "우연히 동일 기물 3개가 모여 2성, 그리고 3성이 완성되면 그 유닛을 '목표 달성'으로 잠금(Lock) 처리합니다."

* **실제 코드 구현**: 
  ```javascript
  let summary = bot.getBenchSummary();
  for (let id in summary) {
      if (unitData && targetTier.includes(unitData.tier) && summary[id] >= 3 && !lockedTargets.includes(id)) {
          if (lockedTargets.length < targetCount) lockedTargets.push(id);
      }
  }
  ```
* **문제점**: `getBenchSummary()` 함수는 2성 유닛을 단순 개수 1개가 아닌 **복사본 개수 3개**로 환산하여 반환합니다 (`u.star === 2 ? 3 : 1`). 따라서 상점에서 1성 기물을 사서 2성이 완성되는 즉시 `summary[id]`가 `3`이 되어 `lockedTargets`에 등록(잠금)됩니다. 
* **영향**: 이는 "3성이 완성되면 잠금"이라는 설명서의 설명과 다릅니다. 실제로는 **"2성이 완성되는 순간 해당 기물을 3성 목표 유닛으로 잠금"**하는 방식으로 작동하고 있습니다. 다행히도 이 방식이 3성을 만들기 위해 특정 유닛을 집중 구매하게 하므로 봇의 지능적 한계를 보완하는 합리적인 구현으로 볼 수 있으나, 설명서의 표현과는 명백히 다릅니다.

### 🥈 8레벨 덱 로직 (`simulate8L`)
8레벨 봇은 4코스트 2성 2개 이상을 목표로 하며, 나머지 자리는 밸류가 높은 순서대로 채워야 합니다. 이 로직에서도 설명서와 다른 추가적인 최적화 코드가 발견되었습니다.

* **설명서 외 추가 구현 (3코스트 구매)**:
  상점에서 `u.tier >= 3`인 유닛을 대기석이 여유로울 때(`bot.bench.length < 8`) 추가로 구매하는 로직이 포함되어 있습니다. 이는 설명서의 "모든 4코스트 유닛을 닥치는 대로 사들입니다"라는 규칙을 벗어나지만, 4코스트 외의 빈자리를 고밸류(3코스트 이상) 유닛으로 채우기 위한 훌륭한 예비 동작입니다.
* **잠금(Lock) 타이밍 오류**:
  ```javascript
  if (unitData && targetTier.includes(unitData.tier) && summary[id] >= 2 && !lockedTargets.includes(id))
  ```
  8레벨 봇은 `summary[id] >= 2`일 때 잠금을 수행합니다. 2성 유닛은 `summary` 값이 `3`이 되므로 정상 잠금되지만, **1성 유닛이 단 2개만 대기석에 있어도** `summary`가 `2`가 되어 아직 2성이 되지 않았음에도 잠금 처리가 되어버립니다. 이는 의도치 않게 목표 유닛을 너무 일찍 확정 짓는 버그성 로직입니다.

### 🥇 9레벨 덱 로직 (`simulate9L`)
9레벨 봇은 180골드를 소모하여 레벨업을 한 뒤, 4코스트와 5코스트 기물로 필드를 도배하는 극단적인 밸류 로직을 가집니다.
* **골드 계산 차이**: 설명서에서는 180골드를 소모하여 9레벨을 찍고 약 70골드가 남는다고 서술되어 있으나, 실제 코드에서는 `TOTAL_GOLD(320) - BASE_LEVEL_COST['9L'](200) = 120 골드`가 남은 상태로 리롤을 시작합니다.
* **로직 검증**: 시너지를 전혀 고려하지 않고, 오직 `u.tier >= 4`인 유닛만 구매하여 밸류가 높은 순서대로 필드에 올리는 로직이 완벽하게 구현되었습니다.

## 3. ⚔️ 전투 및 평가 방식 검증

전투 시스템과 배틀로얄 토너먼트의 진행 방식에 대한 검증 결과입니다.

* **시너지 배제 철학 준수 여부**: 
  봇들이 덱을 빌딩하는 과정(`simulate` 함수군)에서는 시너지 관련 코드가 **단 한 줄도 존재하지 않음**을 확인했습니다. 오직 전투 엔진(`fight` 함수)에서 배치된 덱의 최종 시너지를 판정하여 전투 스탯에 보너스를 주는 방식으로 구현되어 있습니다. 이는 "덱 구성 시 개발자의 편견을 배제하고, 완성된 덱의 결과적 시너지 효과는 게임 규칙대로 적용한다"는 시뮬레이터의 철학에 완벽히 부합합니다.
* **토너먼트 방식의 불일치**:
  * **설명서**: "승리하면 살아남고 패배하면 탈락하는 서바이벌 배틀로얄 토너먼트"
  * **실제 코드**: 400개의 덱이 서로 한 번씩 모두 싸우는 **풀 리그(Round Robin)** 방식 (`line 446-453`)
  * **판단**: 실제 코드는 서바이벌 탈락 방식이 아니라 모든 덱의 총 승률을 공정하게 비교하기 위해 풀 리그로 구현되었습니다. 통계적 신뢰도를 위해서는 풀 리그 방식이 훨씬 우수하지만, 설명서의 "서바이벌 배틀로얄"이라는 단어와는 작동 메커니즘이 다릅니다.

## 4. 🔍 코드 내부의 치명적인 버그 및 개선 포인트

코드 리뷰 과정에서 시뮬레이션의 신뢰성을 떨어뜨릴 수 있는 **치명적인 시스템 버그 2가지**를 발견했습니다.

### 🚨 1. 상점 기물 증발 버그 (기물 풀 고갈 문제)
`rollShop()` 함수에서 상점에 기물을 띄울 때 기물 풀(`this.pool`)에서 해당 기물을 제거합니다.

```javascript
let chosen = randomChoice(tierUnits);
let idx = this.pool.findIndex(u => u.id === chosen.id);
if(idx !== -1) this.pool.splice(idx, 1); // 풀에서 제거
```

* **버그 내용**: 상점에 등장한 5개의 기물 중 봇이 실제로 구매(`buy`)하는 기물은 극히 일부입니다. **구매하지 않고 리롤을 돌려 사라진 상점 기물들은 다시 풀(`this.pool`)로 반환되지 않고 영원히 증발합니다.**
* **치명적 영향**: 봇이 200~300골드를 들고 수십 번의 리롤을 돌리는 동안, 상점에 등장했다가 거절당한 기물들이 모두 사라지면서 기물 풀이 순식간에 고갈됩니다. 이로 인해 리롤 후반부에는 상점에 기물이 아예 뜨지 않거나 특정 코스트의 기물이 고갈되어 시뮬레이션 결과가 심각하게 왜곡됩니다.
* **해결 방안**: 새로운 리롤을 돌리기 전에 기존 상점에 남아있던 미구매 기물들을 다시 봇의 개인 풀(`this.pool`)에 푸시해주는 로직이 반드시 추가되어야 합니다.

### 🚨 2. 합성 시 필드 복귀 누락 버그
`checkCombine()` 함수에서 벤치와 필드(덱)의 기물을 합산하여 합성할 때 발생하는 문제입니다.

```javascript
let upgraded = Object.assign({}, baseUnit);
upgraded.star = star + 1;
this.bench.push(upgraded); // 합성 완료된 기물은 무조건 벤치로 이동
```

* **버그 내용**: 필드(`this.deck`)에 올려둔 2성 유닛 2개와 대기석(`this.bench`)의 2성 유닛 1개가 합쳐져 3성이 되는 경우, 합성된 3성 유닛은 필드가 아닌 **대기석(`this.bench`)으로 이동**합니다.
* **치명적 영향**: 봇들은 전투 배치 단계에서 대기석을 밸류 순으로 정렬하여 필드에 올리기는 하지만, 합성 과정에서 필드의 유닛이 갑자기 대기석으로 빠지면서 필드에 일시적인 빈자리가 생기거나 배치 순서가 꼬이는 현상이 발생할 수 있습니다.

## 💡 종합 권장 개선 코드

위에서 언급한 버그들을 해결하고 설명서의 의도에 완벽하게 부합하도록 개선한 핵심 함수들의 수정 제안입니다.

### 1. `rollShop()` 수정 (기물 증발 방지)
리롤을 돌릴 때 기존 상점에 남아있던 기물을 풀에 반환하는 개념을 적용하거나, 상점 생성 시 임시로 복사하여 풀을 보존하는 방식으로 수정해야 합니다. 가장 간단한 방법은 `rollShop` 호출 시 미구매 기물을 반환하는 처리를 하거나, 상점을 생성할 때 풀에서 직접 꺼내지 않고 확률적 생성 후 구매 시에만 풀에서 차감하는 방식입니다.

```javascript
// 구매 시에만 풀에서 차감하는 방식으로 변경 권장
buy(unit) {
    if (this.gold < unit.tier || this.bench.length >= 30) return false;
    
    // 구매하는 시점에 풀에서 해당 기물 1장 차감
    let idx = this.pool.findIndex(u => u.id === unit.id && u.star === 1);
    if (idx !== -1) {
        this.pool.splice(idx, 1);
    } else {
        return false; // 풀에 남은 기물이 없으면 구매 실패
    }

    this.gold -= unit.tier;
    this.bench.push(Object.assign({}, unit));
    this.checkCombine();
    return true;
}

// 이에 따라 rollShop()은 풀에서 직접 splice하지 않고 단순 참조 및 복사만 수행하도록 수정
```

### 2. 8레벨 봇의 잠금 조건 수정 (`simulate8L`)
1성 기물 2개만으로 잠금되는 현상을 방지하기 위해, 2성 합성이 완료된 유닛만 정확히 판단하도록 수정합니다.

```javascript
// 기존: summary[id] >= 2 (1성 2개만 있어도 잠금됨)
// 변경: 실제 2성(★★) 기물이 대기석에 존재할 때만 잠금
let summary = bot.getBenchSummary();
bot.bench.forEach(u => {
    if (u.tier === 4 && u.star === 2 && !lockedTargets.includes(u.id)) {
        if (lockedTargets.length < targetCount) lockedTargets.push(u.id);
    }
});
```

## 📝 최종 총평

`run_simulation.js`는 **"개발자의 편견(시너지 강제)을 배제하고 깡밸류와 무작위 진화로 최적해를 찾는다"**는 매우 훌륭하고 독창적인 철학을 코드 수준에서 잘 구현해냈습니다. 

특히 덱 빌딩 단계에서는 철저히 시너지를 배제하고, 전투 단계에서만 시너지 스탯을 부여하여 자연스러운 진화·수렴을 유도한 설계는 대단히 뛰어납니다. 다만, **상점 리롤 시 기물이 소멸하는 풀 고갈 버그**와 **잠금(Lock) 조건의 미세한 타이밍 오류**는 시뮬레이션의 통계적 정확도를 저해하므로, 본 보고서의 제안 코드를 반영하여 수정하시는 것을 강력히 권장합니다.
